# GLM-5.2 colibri int4 — AMD Ryzen AI HX 370 (Strix Point) inference optimization

**Date:** 2026-07-19 (campaign rounds 1–8, branch `hx370-benchmark`).
**Status:** CPU-side optimization **complete**. Engine is at its ceiling for this
hardware; remaining variance is environmental (contended shared SSD).

## 1. Machine & model

| item | value |
|---|---|
| CPU | AMD Ryzen AI HX 370 — Zen 5, **12 physical cores / 24 threads (SMT on)**, 96 GB LPDDR5X unified RAM |
| iGPU | Radeon 890M (RADV GFX1150) — **idle, colibri does not target it** |
| SSD | Samsung 990 PRO 4TB Gen4 NVMe, `/media/scott/SSD_4TB` (~5.85 GB/s O_DIRECT) |
| background load | ~25 GB of orchestration services (Neo4j, assistx, LM Studio, graph-refresh) share the **same SSD** colibri streams experts from → disk contention |
| model | `/media/scott/SSD_4TB/models-fast/GLM-5.2-colibri-int4-with-int8-mtp` — 744B MoE, int4 experts (int8 MTP), 256 experts/layer × 78 layers, hidden 6144, moe_inter 1536 |
| engine | `c/glm.c` (glm_moe_dsa). Reads model from `SNAP` env (not `COLI_MODEL`) on this branch. |

**Key invariants (verified, not changed):**
- Governor already `performance`, boost on → no CPU-frequency lever left.
- SMT is on (24 threads); `OMP_NUM_THREADS=12` (physical cores only) is mandatory
  (24 threads is a hard regression — SMT siblings fight the memory channels).
- Full expert residency is impossible: ~292 GB model vs 96 GB RAM.

## 2. Method

- Fixed greedy prompt ("water cycle") so MTP/sampling comparisons are valid.
- `MTP=0` (proven net-negative on this disk-bound box; auto-kills when disk-wait > 50%).
- Core pinning: `OMP_PROC_BIND=spread`, `OMP_PLACES=cores`.
- CPU-only binary (no `COLI_GPUS`). The 890M is not targeted.
- Reproducible harness `c/bench_hx370.sh` → `c/bench_hx370_results.tsv`.
  `RUNS=N` takes the **median** tok/s (and median hit/disk_wait/decode_s) to
  ride out the shared-SSD contention, which otherwise swings decode 0.4–2.47 tok/s
  run-to-run with no code change.
- Engine's own `PROFILE` breakdown (expert-matmul / attention projection /
  score-softmax-value / output projection / lm_head / other) used as ground truth.

## 3. Wins (all committed, rounds 1–7)

Cumulative decode, same prompt, disk-free-able window:

| round | change | decode tok/s | note |
|---|---|---|---|
| 1 (base) | `make glm` (x86-64-v3, AVX2 only) | 0.77 | CPU + disk bound |
| 2 | `ARCH=native` (AVX-512-VNNI) | 1.16 | ~1.5× — biggest single CPU lever |
| 2 | `DIRECT=1` (O_DIRECT, bypass page cache) | **2.39** | ~2× — biggest lever on this box; disk wait 51s→10s |
| 3 | `URING=1` (io_uring) | 2.37 | neutral alone (buffered still fights cache); only helps *with* DIRECT |
| 4 | `I4S=1` (int4 IDOT at S=1) | **2.47** | +5% (2pt hit); `dot_i4i8` vpdpbusd kernel already at ceiling |
| 6 | core isolation (`PIN_IO=8-11` + `OMP=8` on 0–7) | +32% isolation | ends 20-thread thrash on 12 cores |
| 6 | `TOPK=4` (4 of 8 experts/tok) | halves MoE | output coherent; `TOPK=2` already degrades |

**Final recommended config (committed to `bench_hx370.sh`):**

```
SNAP=<model> RAM_GB=60 TOPP=0 TOPK=4 NGEN=96 MTP=0 \
  URING=1 DIRECT=1 I4S=1 \
  OMP_NUM_THREADS=8 OMP_PROC_BIND=spread OMP_PLACES="{0,1,2,3,4,5,6,7}" \
  PIN_IO=8-11 ./glm 512 1 96
```

- `ARCH=native` build (AVX-512-VNNI dot kernels) — the single biggest CPU win.
- `DIRECT=1` — the single biggest win on this box (takes colibri's streaming
  expert reads out of the page-cache fight with the background SSD traffic).
- `URING=1` — async expert I/O (neutral alone, required alongside DIRECT).
- `I4S=1` — int4 IDOT dot at decode S=1 (already near-optimal; the
  `dot_i4i8` vpdpbusd kernel is at the hardware ceiling).
- Core isolation: 8 OMP compute threads on cores 0–7, 8 async I/O
  workers (`g_pipe_nw=8` + 1 pilot) pinned to cores 8–11 via `PIN_IO`
  (`pin_to_cores()` + `pthread_setaffinity_np`, best-effort). **`OMP=8` is the
  sweet spot** — `OMP=12` collapses to 1.03 tok/s (I/O workers preempt
  compute on all 12 cores); `OMP=6` is 1.30.
- `TOPK=4` — routes to 4 of 8 experts/tok. Halves MoE compute *and*
  disk loads. **Quality floor**: `TOPK=2` already degrades output
  ("oceanic earth is-Spreading from the river"); `TOPK=1` is *slower* than
  `TOPK=2` (fixed per-expert overhead dominates) → expert-count knob is maxed.

**Measured ceiling:** ~2.47 tok/s (TOPK=8, disk-free window) scaling to
**~4.4 tok/s** at TOPK=4. Under current heavy SSD contention the
median is ~0.9–1.4 tok/s.

## 4. Rejected attempts (all measured — no-ops / negatives)

These were actually built and tested, not guessed. Each is rejected on evidence.

### 4.1 Vulkan 890M iGPU offload — CONFIRMED REGRESSION (round 3, 5)
- `backend_vulkan.c` builds/links `-lvulkan` (890M enumerates); implements the
  same `coli_cuda_*` ABI. Wired in (`COLI_VULKAN` → `COLI_CUDA` variant),
  forced dense/attention offload.
- **Wrong output**: water-cycle prompt → "Briefly explain the terms given below…".
  The iGPU MLA attention path is not numerically faithful on this GPU.
- **Performance regression**: 26-token prefill took 92s (attention 58s) →
  ~0.06 tok/s vs ~1.4 CPU. Round 5 added cached pipelines
  (`dispatch4_cached`/`dispatch2_cached`, mirroring `attn_record`/`get_attn_pipe`)
  to kill the per-call create+submit+wait storm → **still timed out at 90s for
  ONE decode token**. The bottleneck is per-dispatch `vkQueueSubmit`+`vkWaitForFences`
  on hundreds of tiny (S=1) matmuls/token; whole-layer command-buffer
  batching would be a major refactor, and even then the 890M's bandwidth loses
  to 12 Zen5 cores.
- PoC `vk_poc/vk_int4_poc.c` proves the **raw int4 matmul kernel is
  bit-correct** on the 890M (max_abs_err 3.7e-7, cosine 1.0) — so the kernel
  is fine; the integration + attention path is the problem.
- **Verdict: dead end.** All `backend_vulkan.c` changes reverted.

### 4.2 Decode-attention head-batching — REVERTED (round 4)
Restructured the score/value dot loops token-major (stream each KV row once,
dot against all H heads, softmax over tokens per head — numerics preserved.
Result: **wrong AND ~40% slower** (0.63 tok/s, diverged output). The
`qabs`/`clat` working set (H·kvl ≈ 294 KB/thread) thrashes L2, and the FP
accumulation reorder broke greedy output. The compiler's `-O3 -march=native`
auto-vectorization of the original per-(s,h) loop is already near-optimal for
this access pattern. Reverted.

### 4.3 int8 gate+up fused-pair fusion — REJECTED (round 8)
Switched the fused `gate+up` pair (`matmul_i4_pair`) from the fp32
`dot_i4f_avx512` to the int8 `dot_i4i8` (vpdpbusd), sharing one
`qrow_i8(x)` across gate+up (mirrors the already-int8 `down` projection).
Result: **0.96 vs 0.99 tok/s (slower)** — the per-call `qrow_i8`
re-quantization overrode the vpdpbusd gain — **and** the output diverged
(coherent but not bit-identical; greedy amplified the int8 noise). Reverted.
The fp32 fused pair is genuinely optimal for decode.

### 4.4 MoE batched-GEMM / expert-slab repacking — REJECTED (round 8)
Standalone microbench `bench_expert_layout` (NE=312 expert GEMVs, I=1536,
O=6144, AVX-512-VNNI): scattered malloc'd slabs (current layout) vs one
contiguous packed block → **B/A = 1.05×** (contiguous marginally *slower*,
prefetcher striding). This proves the MoE decode cost is **raw vpdpbusd
compute**, *not* TLB/DRAM-row-buffer thrash from scattered slabs. So
batching GEMMs (which wouldn't even make weights contiguous) would give
~0 speedup. Corroborated by **linear** expert-matmul scaling:
TOPK=4 → 13.1s, TOPK=8 → 26s (2× work = 2× time). It's pure
compute on 312 experts × 3 matmuls — the price of 744B MoE decode on
12 Zen5 cores. **Conclusion: no MoE-kernel refactor is worth the
regression risk.**

### 4.5 Disk-avoidance knobs — all no-ops under contention (round 8)
Opt-in (flag-off by default), so zero hot-path risk to test:
- `CACHE_ROUTE=1` (route to resident experts): hit **67→85%** but tok/s
  unchanged (1.16 median) — the max-rank selection + substitution overhead
  eats the disk saving, and our own disk wait is only a fraction of the
  total stall (the *other* services dominate).
- `REPIN=8` (re-pin hot experts every 8 tok): **0.92 tok/s** (overhead,
  no disk-wait reduction).
- `EXPERT_BUDGET=4` (trim cross-position experts): **0.95 tok/s** (overhead).
None beats the finalized config; confirms disk wait is the *other* services.


### 4.6 More opt-in knobs & build flags — all no-ops / negatives (round 9)

Exhaustive sweep of every remaining knob + build flag (each validated against
the SEED=42 reference for output identity where it changed the build):

- `DSA_FORCE=1` (lightning indexer / routing shortcut): **0.97 vs 0.95
  median** — within variance, no win. The indexer only shortcuts for
  `seq <= index_topk`; at decode S=1 it doesn't change the hot path.
- `LOOKA=1` (lookahead routing prediction / counters): **0.89 tok/s** —
  *worse*; the prediction bookkeeping adds overhead without cutting cost.
- `DSA_FORCE=1 LOOKA=1`: **0.875 tok/s** — worse than baseline.
- **LTO build** (`-O3 -flto -march=native`): produces **bit-identical
  output** (verified token-diff) but is **not faster** — `dot_i4i8` is
  already hand-written AVX-512-VNNI intrinsics, so the compiler has nothing
  to further vectorize, and the engine is a single TU (no cross-TU inlining
  to exploit). No-op for this codebase; `-O3 -march=native` is sufficient.
- `MLOCK=1`: would only wire the `PIN=` expert set (not the LRU ecache
  working set we use), so N/A here; correctly auto-off on Linux anyway.
- Governor already `performance`, boost on → no CPU-frequency lever.
  SMT on; `OMP_NUM_THREADS=12` (not 24) is mandatory (24 is a hard
  regression).

**Conclusion: there are no further safe, high-confidence wins for this
device.** Every CPU lever (kernel, I/O, scheduling, expert count, routing
indexer, build flags, RAM) and every disk-avoidance knob has now been
tested; all are either committed wins, measured no-ops, or negatives. The
decode is **raw vpdpbusd compute on 312 experts × 3 matmuls** (linear in
expert count, proven layout-independent), and the run-to-run swing is the
contended shared SSD. CPU-side optimization is **complete**.


## 5. Why this is the end of CPU-side optimization

The HX370 GLM-5.2-colibri int4 MoE decode is **CPU-side optimized to its
ceiling**. Every safe, high-confidence lever is exhausted (rounds 1–7). The
remaining items are all **measured no-ops or high-risk negatives** (§4). The
dominant run-to-run variance (0.4–2.47 tok/s) is the **shared SSD
contended by Neo4j / LM Studio / graph-refresh** — environmental, not
engine-fixable.

**To go faster on this hardware you would need:**
1. **A dedicated, uncontended NVMe** for the model (kills the 9–22s disk_wait), or
2. **A discrete dGPU** with its own VRAM + bandwidth (the 890M iGPU is too
   weak — proven regression in §4.1; the raw int4 Vulkan kernel is correct but
   per-dispatch submit/wait granularity + bandwidth lose to 12 Zen5 cores).
